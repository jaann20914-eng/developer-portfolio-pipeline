# Notion 데이터베이스 설계

데이터베이스는 네 개만 사용한다. 프로젝트 설명과 재사용 소재를 분리하고, 채용 공고와 PPT 초안을 별도 기록으로 관리한다.

## 관계 구조

```text
프로젝트 1 ── N 포트폴리오 소재
채용 공고 1 ── N PPT 초안
PPT 초안 N ── N 포트폴리오 소재
```

## 1. 프로젝트

한 레코드의 의미: 하나의 개발 프로젝트

| 속성 | 유형 | 용도 |
| --- | --- | --- |
| 프로젝트명 | 제목 | 고유 이름 |
| 한 줄 설명 | 텍스트 | 사용자 관점의 서비스 설명 |
| 기간 | 날짜 | 프로젝트 기간 |
| 역할 | 다중 선택 | 백엔드·프론트엔드·풀스택·모바일·인프라·UI/UX·AI/데이터 |
| 팀 구성 | 텍스트 | 인원과 역할 구성 |
| 내 담당 범위 | 텍스트 | 직접 맡은 영역 요약 |
| 상태 | 선택 | 수집 중·검증 중·활용 가능·보관 |
| 프로젝트 용어표 | 페이지 본문 | 내부 용어와 포트폴리오 표현 |
| 원본 자료 | URL 또는 파일 | 저장소·문서 링크 |
| 공개 범위 | 선택 | 공개 가능·일부 비공개·비공개 |
| 소재 | 관계 | `포트폴리오 소재` 연결 |

페이지 본문에는 `templates/01-project-overview.md`를 사용한다.

## 2. 포트폴리오 소재

한 레코드의 의미: 슬라이드에 독립적으로 선택할 수 있는 개요, 담당 기능, 트러블슈팅, 회고·성과 중 하나

| 속성 | 유형 | 용도 |
| --- | --- | --- |
| 소재명 | 제목 | 문제 또는 결과가 드러나는 이름 |
| 소재 ID | 텍스트 | `OVERVIEW-01`, `CONTRIB-01`, `TS-01`, `RETRO-01` |
| 프로젝트 | 관계 | `프로젝트` 연결 |
| 유형 | 선택 | 개요·담당 기능·트러블슈팅·회고·성과 |
| 순서 | 숫자 | 프로젝트 안 권장 순서 |
| 상태 | 선택 | 자료 수집·초안·검증 대기·승인·보류 |
| 한 줄 결과 | 텍스트 | 공고 선별용 요약 |
| 역할 | 다중 선택 | 실제 담당 역할 |
| 강점 태그 | 다중 선택 | 통제 목록 사용 |
| 영향 태그 | 다중 선택 | 통제 목록 사용 |
| 기술 태그 | 다중 선택 | 현재 프로젝트에서 확인한 기술만 사용 |
| 기여 형태 | 선택 | 직접 구현·공동 설계/구현·팀 전체 |
| 발생 성격 | 선택 | 운영 발생·개발 중 발견·테스트 재현·잠재 위험 분석·해당 없음 |
| 증거 수준 | 선택 | A·B·C·D |
| 정량 근거 | 체크박스 | 전후 수치와 조건이 모두 있을 때만 선택 |
| 한계 포함 | 체크박스 | 한계·부작용이 본문에 있는지 확인 |
| 원본 근거 | URL 또는 파일 | 코드·테스트·로그·측정 문서 |
| 공개 가능 | 체크박스 | 민감 정보 제거 확인 |
| 최종 검토일 | 날짜 | 마지막 사실 검증일 |

본문 템플릿:

- 개요: `templates/01-project-overview.md`의 개요 페이지 후보 문구
- 담당 기능: `templates/02-my-contribution.md`
- 트러블슈팅: `templates/03-troubleshooting.md`
- 회고·성과: `templates/04-retrospective-outcomes.md`

## 3. 채용 공고

한 레코드의 의미: 한 회사의 한 직무 공고

| 속성 | 유형 | 용도 |
| --- | --- | --- |
| 회사·직무 | 제목 | 지원 단위 |
| 공고 URL | URL | 원문 |
| 마감일 | 날짜 | 일정 |
| 상태 | 선택 | 검토·지원 준비·지원 완료·종료 |
| 핵심 업무 | 텍스트 | 공고에서 반복되는 실제 업무 |
| 요구 역할 | 다중 선택 | 역할 태그 |
| 요구 강점 | 다중 선택 | 강점 태그 |
| 요구 기술 | 다중 선택 | 기술 태그 |
| 우선순위 메모 | 텍스트 | 필수·우대 구분과 해석 |
| PPT 초안 | 관계 | `PPT 초안` 연결 |

공고 원문은 페이지 본문에 보존한다. 요약만 저장해 원문의 조건을 잃지 않도록 한다.

## 4. PPT 초안

한 레코드의 의미: 특정 공고 또는 목적에 맞춘 한 번의 포트폴리오 구성

| 속성 | 유형 | 용도 |
| --- | --- | --- |
| 초안명 | 제목 | `회사-직무-날짜` 권장 |
| 채용 공고 | 관계 | `채용 공고` 연결 |
| 선택 소재 | 관계 | `포트폴리오 소재` 다중 연결 |
| 목표 페이지 수 | 숫자 | 분량 제한 |
| 원본 PPT | URL 또는 파일 | 레이아웃 템플릿 |
| 페이지 원고 | URL 또는 파일 | 승인된 TXT·MD |
| 결과 PPT | URL 또는 파일 | 생성된 PPTX |
| 상태 | 선택 | 소재 선별·원고 작성·페이지 검토·PPT 반영·검증 완료 |
| 최종 검증일 | 날짜 | 렌더링·텍스트 대조 완료일 |
| 확인 필요 수 | 숫자 | 0이 되어야 검증 완료 가능 |

본문에는 `templates/05-deck-plan.md`를 사용한다.

## 권장 뷰

### 프로젝트

- `활용 가능 프로젝트`: 상태가 활용 가능인 항목
- `자료 보완 필요`: 상태가 수집 중 또는 검증 중인 항목

### 포트폴리오 소재

- `프로젝트별 소재`: 프로젝트로 그룹, 순서 오름차순
- `트러블슈팅 뱅크`: 유형이 트러블슈팅인 항목
- `공고 매칭 가능`: 상태 승인, 공개 가능 체크, 증거 수준 A~C
- `근거 보완`: 상태 검증 대기 또는 증거 수준 D
- `강점별 소재`: 강점 태그로 그룹

### 채용 공고

- `지원 준비`: 상태가 검토 또는 지원 준비
- `마감일`: 캘린더 뷰

### PPT 초안

- `제작 중`: 검증 완료 전 상태
- `완료본`: 상태가 검증 완료

뷰 필터는 접근권한이 아니다. 비공개 프로젝트나 민감 자료는 공유 권한과 저장 위치에서 별도로 보호한다.

## 생성 순서

1. `프로젝트` 생성
2. `포트폴리오 소재` 생성 후 프로젝트 관계 연결
3. `채용 공고` 생성
4. `PPT 초안` 생성 후 공고·소재 관계 연결
5. 속성이 모두 생긴 뒤 권장 뷰 생성
6. 프로젝트 페이지에 해당 프로젝트 소재의 연결된 뷰 배치

## 검증 질문

- 프로젝트별로 개요·담당 기능·트러블슈팅·회고가 한눈에 보이는가
- 트러블슈팅만 모아 강점 태그로 필터링할 수 있는가
- 공고 하나에서 선택 소재와 PPT 초안으로 바로 이동할 수 있는가
- 근거가 약하거나 확인이 필요한 소재가 승인 소재와 섞이지 않는가
- 비공개 자료가 뷰 필터만으로 보호된다고 오해할 구조가 아닌가
