# 포트폴리오 레이아웃 명세

이 문서는 슬라이드의 정보 구조, 배치 역할, 영역 좌표만 정의한다. 글꼴, 크기, 굵기, 색상, 장식 스타일은 정의하지 않는다. 시각 값은 `design-tokens.md`의 범용 기본값 또는 `tokens-current-deck.md`의 현재 덱 기준값에서 역할 이름(`lead`, `section_title` 등)으로 찾는다.

## 적용 우선순위

1. 사용자가 지정한 기존 PPT 레이아웃
2. 사용자가 승인한 페이지별 구성표
3. 이 문서의 기본 레이아웃

기존 PPT에 텍스트만 적용하는 작업에서는 도형의 위치, 크기, 슬라이드 수, 이미지 영역을 변경하지 않는다. 이 문서는 어떤 내용을 어느 영역에 넣을지 판단할 때, 그리고 같은 형식의 덱을 새로 구성할 때 사용한다.

## 기본 덱 구성

```text
1      표지                      L01
2      이력 · 목차               L02
3      작업 방식                 L03
프로젝트마다 반복
  ├─ 프로젝트 개요 · 담당 기능   L04   1장
  ├─ 트러블슈팅                  L05 또는 L06   1~2장
  └─ 성과 · 회고                 L07   1장
```

- 프로젝트 구분 페이지는 두지 않는다. 프로젝트 전환은 L02 목차와 모든 페이지 제목의 `프로젝트명:` 접두어로 표시한다.
- 별도의 자기소개 페이지는 두지 않는다. 소개 문구는 L01 표지에 둔다.

## 공통 화면 구조

슬라이드 크기: 13.33 × 7.5in (16:9)

```text
┌──────────────────────────────────────────────────────┐
│ 제목 (프로젝트명: 결과·주제)                   쪽 번호 │
│ 문제 요약 2줄 (트러블슈팅만)                          │
├──────────────────────────┬───────────────────────────┤
│ 텍스트 영역               │ 시각 자료 영역             │
│ 섹션 제목 → 본문 반복      │ 도식 · 대표 화면 · 차트    │
│                          │                           │
└──────────────────────────┴───────────────────────────┘
```

| 공통 요소 | 좌표 (in) | 규칙 |
| --- | --- | --- |
| 제목 | x 0.50, y 0.40, 폭 12.33 | `프로젝트명: 결과 또는 주제`. 표지·이력·작업 방식 페이지는 접두어 없음 |
| 쪽 번호 | x 12.23, y 0.60, 폭 0.60 | 오른쪽 위. 자동 쪽 번호 필드 사용 |
| 왼쪽 텍스트 열 | x 0.46~0.50, 폭 약 6.0 | 섹션 제목과 본문을 위에서 아래로 쌓음 |
| 오른쪽 시각 자료 영역 | x 7.4~12.8 | 페이지 유형별로 도식·화면·차트 중 하나 |

## 공통 영역

| 영역 ID | 역할 | 필수 여부 | 배치 원칙 |
| --- | --- | --- | --- |
| `title` | 페이지의 실제 주제 또는 결과 | 필수 | 슬라이드 상단, `프로젝트명:` 접두어, 한 가지 메시지 |
| `lead` | 제목 아래 문제의 원인 구조를 2줄로 요약 | 트러블슈팅에서 필수 | 제목 바로 아래, 아래에 짧은 구분선 |
| `content-primary` | 가장 중요한 흐름·비교·결과 | 필수 | 시선이 먼저 닿는 중심 영역 |
| `content-secondary` | 원인·설계·보조 설명 | 선택 | 핵심 메시지보다 시각적 우선순위 낮춤 |
| `evidence` | 전후 수치·측정 조건 | 필요 시 필수 | 주장과 가까운 위치, `라벨  수치` 형식 |
| `regression` | 회귀·사이드 이펙트 확인 결과 | 트러블슈팅에서 필수 | 결과 바로 아래. 확인된 결과만 기록 (통과 테스트 수, 누락·중복·오염 0건, 기존 처리 유지) |
| `limits` | 남은 한계·후속 과제 | 사용 안 함 (기본값) | 슬라이드에 넣지 않고 발표자 노트·면접 대비 자료로 보냄. 사용자가 요청할 때만 슬라이드에 배치 |
| `visual` | 도식·대표 화면·차트 | 페이지 유형별 | 오른쪽 시각 자료 영역 |
| `meta` | 기간·인원·담당·링크 | 개요 페이지에서 필수 | 제목 아래 왼쪽, 본문 흐름을 방해하지 않는 위치 |
| `notes` | 발표자 노트 | 모든 페이지 | `[N페이지]` 표기 + 면접 대비 근거(측정 조건, 코드 위치, 남은 한계) |

## 페이지 유형

### L01. 표지

목적: 지원자의 정체성, 개발 관점, 연락처 전달

```text
                                  [보조 슬로건 1줄]
                                  [메인 슬로건 1줄]

                                            [이름]
                                       [연락처 3줄]

[사진]  [소개 핵심 문장 1줄]
        [소개 보충 2줄]
```

| 요소 | 좌표 (in) | 규칙 |
| --- | --- | --- |
| 슬로건 2줄 | x 0.50, y 0.79, 폭 12.33, 오른쪽 정렬 | 보조 슬로건 1줄 + 메인 슬로건 1줄. 이후 프로젝트로 증명할 수 있는 관점만 |
| 이름 | x 10.29, y 2.36, 폭 2.54 | 이름만 |
| 연락처 | x 10.29, y 2.75, 폭 2.54 | 이메일 · 전화 · GitHub 3줄 |
| 사진 | x 0.50, y 5.58, 1.18 × 1.57 | 선택 |
| 소개 문구 | x 1.81, y 6.48, 폭 4.94 | 핵심 문장 1줄 + 보충 2줄. 표지에서만 문장형 서술 허용 |
| 배경 장식 | 전체 화면 | 선택. 글자 영역과 겹치지 않게 |

- 프로젝트 상세 내용 배치 금지

### L02. 이력 · 목차

목적: 학력·경력·자격과 포트폴리오 구성을 한 장에서 전달

```text
[교육]                     │  p.03      [작업 방식 이름]
[경력]                     │            [한 줄 설명]
[수상]                     │  p.04-07   [프로젝트명]
[자격]                     │            [한 줄 설명]
[기술 스택]                │            [기간 / 인원 / 역할]
  ●●●○○ Lv.3  [기술 묶음]   │  ...
  ●●○○○ Lv.2  [기술 묶음]   │
```

| 요소 | 좌표 (in) | 규칙 |
| --- | --- | --- |
| 왼쪽 이력 열 | x 0.50, y 0.85부터, 폭 약 5.2 | 교육 → 경력 → 수상 → 자격 → 기술 스택 순서. 항목은 `기간  내용` |
| 세로 구분선 | x 6.67, y 0.85~6.87 | 두 열 구분 |
| 오른쪽 목차 열 | x 7.42, 폭 5.41 | 항목마다 `p.시작-끝   이름` + 한 줄 설명 + 기간·인원·역할(프로젝트만) |

- 기술 스택은 5칸 점(●○)과 `Lv.N`으로 표시하고, 같은 수준의 기술을 한 묶음으로 나열한다. 실제 숙련도보다 높게 칠하지 않는다.
- 목차 항목은 덱의 실제 순서대로 배치하고, 항목 사이 간격을 일정하게 둔다.

### L03. 작업 방식

목적: 개발 과정에서 결정·구현·검증을 어떻게 나누고 확인하는지 전달

```text
[리드 3줄]

[00 단계]   [01 단계]   [02 단계]   [03 단계]   [04 단계]
[설명]      [설명]      [설명]      [설명]      [설명]
              ↑ 반복 구간 라벨 ↑
[산출물]    [산출물]    [산출물]    [산출물]    [산출물]
[도구·규칙] [도구·규칙] [도구·규칙] [도구·규칙] [도구·규칙]
```

| 요소 | 좌표 (in) | 규칙 |
| --- | --- | --- |
| 리드 | x 0.50, y 1.35, 폭 7.46 | 작업 방식 전체를 3줄로 요약 |
| 5단계 열 | x 0.63 / 3.15 / 5.66 / 8.18 / 10.69, 폭 2.07 | 열마다 같은 폭과 간격 |
| 1층 단계 설명 | y 2.78 | `00  단계명 (핵심 행동)` + 1~2줄 |
| 반복 구간 라벨 | 1층과 2층 사이 | 반복이 실제로 있는 단계 사이에만 화살표와 함께 표시 |
| 2층 산출물 | y 4.71 | 산출물 이름 + 1줄 |
| 3층 도구·규칙 | y 5.41 | 도구·문서 이름 + 2줄 |

- 각 단계의 근거(문서명, 날짜, 횟수)는 발표자 노트에 둔다.

### L04. 프로젝트 개요 · 담당 기능

목적: 처음 보는 사람이 서비스, 팀, 직접 담당 범위를 한 장에서 이해

```text
[기간]
[인원 구성 (담당: …)]            [배경]
[GitHub]                         [목표]
[대표 화면]                      [주요 기능 •]
                                 [담당 기능]
[로고 ×3] [기술 선택 이유 2줄]     [소제목] [1줄 설명] ×2
```

| 요소 | 좌표 (in) | 규칙 |
| --- | --- | --- |
| 메타 | x 0.50, y 1.35, 폭 약 6.0 | 기간 / 인원 구성 (담당 범위) / GitHub 주소 |
| 대표 화면 | x 0.50, y 2.06, 약 6.74 × 4.21 | 웹은 화면 1장, 앱은 화면 여러 장 + 단계 캡션 허용 |
| 기술 로고 | x 0.50 / 0.96 / 1.42, y 약 6.4, 0.32 × 0.32 | 핵심 기술 3개 |
| 기술 선택 이유 | x 1.98, y 약 6.35, 폭 5.26 | 2줄. 기술 이름보다 해결한 문제를 먼저 |
| 오른쪽 텍스트 열 | x 7.70, y 1.62부터, 폭 5.15 | 배경 → 목표 → 주요 기능 → 담당 기능 순서 |

- 배경·목표는 사용자 문제와 서비스의 해결 방식을 기술 스택보다 먼저 쓴다.
- 주요 기능은 팀 전체 기능 4개 안팎을 `•` 목록으로 쓴다.
- 담당 기능은 `소제목(기능명) + 1줄 설명`을 2개 안팎으로 써서 팀 기능과 직접 담당 범위를 구분한다.

### L05. 트러블슈팅 (1건)

목적: 문제의 원인, 개선, 결과, 회귀 확인을 한 장에서 전달

```text
[제목: 프로젝트명: 결과]
[문제 요약 2줄]                 ┌ Before 도식 ┐
──────────                      │             │
01  원인 / 기존 설계              └─────────────┘
02  개선 과정 (•)                ┌ After 도식  ┐
03-1  결과 (라벨  수치)          │             │
03-2  회귀·사이드 이펙트 확인 결과 └─────────────┘
```

| 요소 | 좌표 (in) | 규칙 |
| --- | --- | --- |
| 문제 요약 | x 0.46, y 1.35, 2줄 | 원인 구조와 그 결과를 2줄로 |
| 구분선 | x 0.50, y 2.00, 폭 약 5.3 | 문제 요약과 본문 구분 |
| 왼쪽 본문 열 | x 0.46, 폭 약 6.05 | 섹션 행 격자: 01 = y 2.32 / 02 = y 3.34 / 03-1 = y 4.57 / 03-2 = y 5.79 |
| Before 도식 | x 7.56, y 1.35, 5.27 × 2.65 | 기존 구조 |
| After 도식 | x 7.56, y 4.10, 5.27 × 2.65 | 개선 구조. Before와 같은 구체성 수준 |

섹션별 내용:

| 섹션 | 분량 | 형식 |
| --- | --- | --- |
| `01  원인 / 기존 설계` | 2줄 | 구조를 설명하는 명사형 문장 |
| `02  개선 과정` | 2~3개 | `•` 목록 |
| `03-1  결과` | 2~3줄 | `라벨  전 → 후  변화율` |
| `03-2  회귀·사이드 이펙트 확인 결과` | 2줄 | 확인된 결과만 |

도식 형식은 내용에 맞는 하나를 고른다.

- 구조 비교형: 서버·채널·사용자 사이의 전달 방식이 핵심일 때. 위 Before / 아래 After 두 칸.
- 순서도형: 여러 시스템 사이의 요청 순서가 핵심일 때. 시스템 축(예: 저장소 / 앱 / 서버)을 세로선으로 두고 `공통 → Before → After` 구간을 위에서 아래로 배치. 생략된 호출은 흐린 점선과 `생략` 라벨.
- 두 형식 모두 글자는 키워드만, 강조할 차이만 그리고, 결과는 `X 코드` / `O 코드` 표시로 끝낸다.

### L06. 트러블슈팅 (2건)

목적: 짧은 문제 두 건을 한 장에 나란히 전달

```text
[제목]
[문제 1 요약 2줄]                [문제 2 요약 2줄]
01  원인 / 기존 설계              01  원인 / 기존 설계
02  개선 과정                     02  개선 과정
03-1  결과                        03-1  결과
03-2  회귀·사이드 이펙트          03-2  회귀·사이드 이펙트
```

| 요소 | 좌표 (in) | 규칙 |
| --- | --- | --- |
| 왼쪽 열 | x 0.46, 폭 5.67 | 문제 1 |
| 오른쪽 열 | x 7.16, 폭 5.69 | 문제 2 |
| 문제 요약 | y 1.35 | 두 열 모두 2줄 |
| 섹션 행 격자 | 01 = y 2.32 / 02 = y 3.34 / 03-1 = y 4.77 / 03-2 = y 5.99 | 두 열의 같은 섹션 제목을 같은 높이에 둔다. 높이가 다르면 더 긴 쪽에 맞춘다 |

- 도식은 두지 않는다.
- 각 건의 02 개선 과정이 3개 이하이고 결과가 2~3줄일 때만 사용한다. 넘치면 L05 두 장으로 나눈다.

### L07. 성과 · 회고

목적: 직접 성과와 팀 성과를 구분하고, 다음 프로젝트에 적용할 판단 원칙 정리

```text
[제목: 프로젝트명: 성과와 회고]
대외 성과 (없으면 생략)            [개선율 가로 막대 차트]
주요 성과        라벨  내용 ×3~4
프로젝트 전체 성과 라벨  내용 ×2
배운 점          라벨  원칙 ×2~3
```

| 요소 | 좌표 (in) | 규칙 |
| --- | --- | --- |
| 왼쪽 텍스트 열 | x 0.46, y 1.80부터, 폭 6.02 | 대외 성과 → 주요 성과 → 프로젝트 전체 성과 → 배운 점 |
| 차트 | x 7.41, y 1.80, 약 5.42 × 4.1~4.5 | 편집 가능한 PPT 차트 |

- `대외 성과`는 수상·선정 등 외부 결과가 있을 때만 둔다. 빈 섹션은 만들지 않는다.
- `주요 성과`는 직접 구현 성과, `프로젝트 전체 성과`는 팀 전체 결과로, 섹션을 나눠 구분한다.
- `배운 점`은 감상이 아니라 재사용할 판단 원칙으로 쓴다.
- 아쉬운 점·핵심 회고 섹션은 두지 않는다. 남은 위험은 발표자 노트로 보낸다.
- 차트 값은 같은 프로젝트의 트러블슈팅 결과 또는 이 페이지 본문에 있는 수치만 사용한다. 감소율로 비교하기 어려운 지표는 개선 전·후 두 계열 막대로 표시한다.

## 쪽수 규칙

- 프로젝트마다 L04 1장, 트러블슈팅 1~2장, L07 1장
- 트러블슈팅 2건을 한 장(L06)에 넣는 것은 각 건이 짧을 때만
- 페이지를 넣거나 빼면 L02 목차의 `p.시작-끝` 범위, 쪽 번호, 발표자 노트의 `[N페이지]` 표기를 함께 고친다

## 정보 밀도 규칙

- 한 페이지에 중심 메시지 하나
- 제목과 본문에서 같은 문장 반복 금지
- 텍스트 박스 수를 늘리기보다 문장 우선순위 조정
- 모든 섹션을 억지로 채우지 않고 해당 페이지에 필요한 영역만 사용
- 설명이 넘치면 페이지를 임의로 추가하기 전에 문장을 압축하고 사용자에게 분량 변경 확인
- 수치, 단위, 비교 대상, 회귀 확인 결과는 공간 부족을 이유로 우선 삭제하지 않음
